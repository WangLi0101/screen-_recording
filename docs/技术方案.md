# 屏幕录制工具 · 技术方案

> 配套文档：《需求文档》《竞品调研》　｜　更新：2026-11-16　｜　状态：待评审
>
> 本文给出技术选型、架构、关键链路与风险验证清单。所有版本号于 2026-11-16 通过 npm registry 与实际文档核对。

---

## 1. 约束与目标

- 桌面端：Windows 优先（10 22H2+ / 11），macOS 13+ 同版本跟进，Linux 降级支持。
- 全程本地处理，不上传任何录制内容；网络仅用于检查更新（可关闭）。
- 1080p30 录制时 CPU 增量 < 8%（8 核参考机），丢帧率 < 0.5%，24 小时连续录制不崩溃。
- 录制中断（断电/崩溃/强杀）后最多丢失 2 秒素材。
- 安装包单平台 < 120 MB，空闲内存 < 150 MB。

## 2. 技术栈

| 层 | 选型 | 版本 | 说明 |
| --- | --- | --- | --- |
| 运行时 | Electron | 45.3.3 | Chromium 侧提供 `desktopCapturer`、WebCodecs、MediaStreamTrackProcessor |
| 构建 | Vite | 8.3.8 | Vite 8 已用 Rolldown 统一打包（2026-03 稳定），构建快 10–30× |
| 构建集成 | electron-vite | 6.0.0 | peer 依赖声明支持 `vite ^8`，内置 main/preload/renderer 三套配置与 HMR |
| React 插件 | @vitejs/plugin-react | 6.x | v6 用 Oxc 做 React Refresh，不再依赖 Babel |
| UI | React | 19.3.1 | 并发渲染；录制状态用外部 store 驱动，避免频繁重渲染 |
| 语言 | TypeScript | 5.9.x | 全量 strict，IPC 契约共享类型 |
| 样式 | Tailwind CSS 4 + shadcn/ui (Radix) + lucide-react | — | 暗色优先、可键盘操作 |
| 状态 | Zustand | 5.x | 轻量、可跨窗口同步（配合 IPC 广播） |
| 校验 | Zod | 4.x | 设置、项目文件、IPC 入参校验 |
| 封装 | mp4-muxer（备选 mediabunny） | 最新 | 浏览器内流式 fMP4 封装，支持 Worker |
| 转码 | ffmpeg（随包内置，`resources/ffmpeg/<platform>-<arch>/`） | 6.1.1（目标 LGPL 构建） | 仅做封装/裁剪/转码，不承担采集；不依赖用户机器上的 ffmpeg（见 §14） |
| 全局输入 | uiohook-napi（P1） | 最新 | 全局键鼠事件；需原生模块与平台权限（见 §9） |
| 存储 | `node:sqlite`（Electron 内置 Node ≥22.5）或 JSON 索引 | — | MVP 用 JSON 索引，V1 迁 SQLite，避免 better-sqlite3 重编译 |
| 打包 | electron-builder | 26.x | NSIS / DMG，ffmpeg 走 extraResources 按平台-架构裁剪 |
| 更新 | electron-updater | 6.x | 签名校验 + 灰度 |
| 测试 | Vitest + Playwright (`_electron`) | — | 单测时间轴/封装，E2E 走真实录制链路 |

**为什么是 electron-vite 而不是 Electron Forge + Vite 插件：** Forge 的 Vite 插件对 Vite 8 / Rolldown 的跟进滞后，且多入口（主窗、控制条、区域选择、录制器）配置更繁琐；electron-vite 6 已显式声明 `vite ^8` 兼容。

**为什么不用 MediaRecorder 作为主链路：** 码率控制粗、无法精确暂停/续录、无法保证恒定帧率与时间戳、分段与崩溃恢复困难、封装格式受浏览器实现限制。MediaRecorder 仅作为兜底（见 §4）。

## 3. 总体架构

```
┌──────────────────────────── Main Process ────────────────────────────┐
│ app / 单实例 / 托盘 / globalShortcut / powerSaveBlocker               │
│ WindowManager: 主窗口 · 控制条 · 区域选择遮罩 · 录制器(隐藏)          │
│ CaptureService: desktopCapturer.getSources + setDisplayMediaRequestHandler │
│ StorageService: 素材索引 / 设置 / 恢复清单 (JSON→SQLite)              │
│ ExportService: ffmpeg 子进程 / 硬件编码探测 / 进度与取消              │
│ PermissionService: TCC / 麦克风隐私 / Wayland 检测                    │
└───────────────▲───────────────────────────────▲──────────────────────┘
                │ typed IPC (invoke)            │ MessagePort (二进制分片)
┌───────────────┴───────────────┐   ┌───────────┴──────────────────────┐
│ Renderer: UI                  │   │ Renderer: Recorder (hidden)      │
│ 素材库 / 预览编辑 / 设置      │   │ getDisplayMedia                  │
│ 录制准备 / 导出进度           │   │ MediaStreamTrackProcessor        │
└───────────────────────────────┘   │ Canvas 裁剪/合成 → VideoEncoder   │
                                    │ AudioWorklet 混音 → AudioEncoder │
                                    │ Worker: mp4-muxer → 分片         │
                                    └───────────┬──────────────────────┘
                                                │ 每 2s 一个 fMP4 分片
                                        ┌───────▼────────┐
                                        │ 磁盘 .part/    │
                                        │ init.mp4 + N   │
                                        └────────────────┘
```

**录制器放在独立隐藏窗口的原因：** 与 UI 解耦（主窗口关闭、页面跳转不影响录制）；避免 React 重渲染干扰管线；崩溃时只有录制器进程受影响，主进程可拉起恢复流程。

## 4. 采集方案对比与选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **A. `getDisplayMedia` + WebCodecs** | 跨平台、Electron 原生支持、硬件编码、逐帧时间戳、可精确暂停、可 Worker 封装 | 需自行实现裁剪/合成/封装；光标由系统合成，无法剔除 | ✅ 主链路 |
| B. `getDisplayMedia` + MediaRecorder | 实现最快（约 100 行） | 码率/帧率不可控、暂停有空洞、WebM 为主、分段困难 | 兜底 / POC 对照 |
| C. 原生 FFmpeg 采集（ddagrab / gdigrab / avfoundation / pipewire） | 稳定、可脱离 Chromium、易做无光标采集 | 平台分支多、无法采集受保护内容、与 Electron 生命周期耦合、包体大 | 仅 V2 评估（无光标/高帧率场景） |
| D. 原生 SDK（Windows Graphics Capture / ScreenCaptureKit） | 画质与性能最佳、可拿光标开关 | 需 N-API 原生开发与签名，工作量 ≥ 4 周 | 不做 |

**采集主链路：**

```ts
// main: 只在这里拿 source，renderer 不能直接调 desktopCapturer
session.defaultSession.setDisplayMediaRequestHandler(async (request, callback) => {
  const sources = await desktopCapturer.getSources({
    types: ['screen', 'window'],
    thumbnailSize: { width: 320, height: 180 },
    fetchWindowIcons: true,
  })
  const chosen = pickerState.selectedSource // 由 UI 选择后写入
  const source = sources.find((s) => s.id === chosen)
  if (!source) return callback(null)
  callback({
    video: source,
    audio: config.systemAudio ? 'loopback' : undefined, // Win/mac 系统音频
  })
})
```

```ts
// recorder renderer
const stream = await navigator.mediaDevices.getDisplayMedia({
  video: { frameRate: { ideal: fps, max: fps } },
  audio: config.systemAudio, // 依赖 handler 里返回 'loopback'
})
const [videoTrack] = stream.getVideoTracks()
const processor = new MediaStreamTrackProcessor({ track: videoTrack })
const reader = processor.readable.getReader()
// reader.read() → VideoFrame（携带 timestamp，单位微秒）
```

要点：

- `desktopCapturer` 只能在主进程调用；缩略图通过 IPC 以 dataURL 传给 UI。
- `getDisplayMedia` 不支持用 `deviceId` 指定源，必须由 handler 决定；自定义选择器体验优于系统选择器，`useSystemPicker: true` 作为兜底（实验性）。
- 录制器窗口必须 `backgroundThrottling: false`；管线不依赖 `requestAnimationFrame`，隐藏窗口也能稳定出帧。

## 5. 视频管线

```
VideoFrame ──► (区域裁剪/缩放, OffscreenCanvas 2D/WebGL) ──► VideoEncoder(H.264)
                                                              │ EncodedVideoChunk
                                                              ▼
                                                    Worker: mp4-muxer
                                                              │ 每 ~2s flush
                                                              ▼
                                                   IPC(MessagePort) → fs.appendFile
```

### 5.1 编码参数

| 场景 | 分辨率 | 帧率 | 码率 | 关键帧间隔 |
| --- | --- | --- | --- | --- |
| 标准 | 1920×1080 | 30 | 8 Mbps | 2 s |
| 流畅 | 1920×1080 | 60 | 12 Mbps | 2 s |
| 高清 | 2560×1440 | 30 | 16 Mbps | 2 s |
| 超清 | 3840×2160 | 30 | 30 Mbps | 2 s |

```ts
const config: VideoEncoderConfig = {
  codec: 'avc1.640028',            // High Profile L4.0，按分辨率上调 level
  width, height,                    // 必须为偶数（H.264 约束）
  bitrate,
  framerate: fps,
  latencyMode: 'realtime',
  hardwareAcceleration: 'prefer-hardware',
  avc: { format: 'avc' },           // mp4 需要 AVCC（长度前缀 + description）
}
const support = await VideoEncoder.isConfigSupported(config)
// 不支持则降级：'prefer-software' → 再降级 MediaRecorder
```

### 5.2 区域录制与 HiDPI

Electron 无法让 `getDisplayMedia` 只采一块区域，因此采用**整屏采集 + 裁剪**：

1. 区域选择遮罩按显示器分别创建全屏透明窗口，用户拖拽得到 DIP 矩形。
2. 用 `screen.getAllDisplays()` 匹配 `display_id`，取 `scaleFactor`，换算为物理像素。
3. 在 OffscreenCanvas 上 `drawImage(frame, -cropX, -cropY, ...)`，宽高向下取偶。
4. 裁剪后再编码，码率按裁剪后分辨率计算（不是整屏），避免浪费。

代价：整屏帧仍要过一次 GPU 拷贝，4K 屏裁剪录制约有 2–4% 额外占用。可接受。

> 若后续要"区域录制只采该区域"以进一步降帧开销，需要原生采集后端（方案 D），不在 V1 范围。

### 5.3 多显示器与分辨率变化

- 录制中监听 `screen` 的 `display-added/removed/metrics-changed`：分辨率变化时**重建编码器**（新分片），并在时间轴打点，导出时统一缩放到目标画布（letterbox），避免花屏。
- 显示器休眠/切换会导致帧时间戳跳变，需检测 `frame.timestamp` 间隔 > 2s 时插入静帧或标记 gap。

### 5.4 帧时间戳与暂停

- 以 `VideoFrame.timestamp` 为主时钟；暂停时停止读取并记录 `pauseStartedAt`，恢复后所有时间戳减去累计暂停时长。
- 不用 `performance.now()` 作为视频时间轴，避免与采集时钟漂移。

## 6. 音频管线

```
系统音频 track ┐
麦克风 track   ┴─► AudioContext ─► GainNode(各自音量) ─► MediaStreamDestination
                                                         │
                                                   AudioWorklet (PCM 采集/重采样)
                                                         │
                                          AudioEncoder(AAC) 或 PCM 落盘
```

### 6.1 平台差异（必须实现为能力探测，而不是硬编码）

| 平台 | 系统音频 | 关键条件 |
| --- | --- | --- |
| Windows 10 2004+ / 11 | ✅ loopback（默认输出设备的整机混音） | `callback({ audio: 'loopback' })` + `getDisplayMedia({ audio: true })`；**不支持按进程单独采集** |
| macOS 13+ | ✅ | 需屏幕录制权限；14.2+ 走 CoreAudio Tap，需要 `NSAudioCaptureUsageDescription` + "系统音频录制" TCC 授权 |
| macOS ≤12.7.6 | ❌ | 只能借助 BlackHole 等虚拟声卡 |
| Linux PipeWire | ◐ | portal 一次只允许一个源；无 monitor source 时拿不到系统音 |

> **高优先级坑（官方文档明确）：** macOS 14.2+ 权限缺失或被拒时，`desktopCapturer` **仍会返回一条 audio track，但状态为 `ended`、永远不出样本，且不抛错**。必须主动检测：`systemPreferences.getMediaAccessStatus('screen' | 'microphone')` + 录制前 3 秒电平探测，静音则弹权限引导，禁止"假装在录"。

### 6.2 混音与音量

- 系统音与麦克风各自 `GainNode`，默认 1.0 / 1.0，UI 提供独立推子与实时电平。
- 混音后单轨写入（MVP），保留双轨能力（V1，便于后期单独静音/降噪）。
- 麦克风降噪：P1 引入 RNNoise（WASM，Worker 内处理），不引入云端。
- 采样率统一 48 kHz；若设备不支持，用 `AudioContext({ sampleRate: 48000 })` 让浏览器重采样。

### 6.3 AAC 的现实问题

`AudioEncoder` 对 AAC 的支持随平台/版本不同（部分构建只有 Opus）。策略：

1. POC 验证 `AudioEncoder.isConfigSupported({ codec: 'mp4a.40.2', ... })`。
2. 支持 → AAC 直封 MP4。
3. 不支持 → 音频以 PCM/Opus 旁路落盘，停止后用 ffmpeg 编码 AAC 并封装（多一次 IO，但只发生在停止时）。
4. 视频与音频分别落盘、停止时合并，是天然容错设计（任一路失败仍可导出另一路）。

## 7. 容器、落盘与崩溃恢复

- 采用 **fragmented MP4**：`mp4-muxer` 的 `fastStart: 'fragmented'`，启动时写一次 `ftyp + moov`（init 段），之后每 ~2 秒一个 `moof + mdat` 分片。
- 目录结构：

```
%APPDATA%/ScreenRec/<recordingId>/
  init.mp4
  seg-00001.m4s
  seg-00002.m4s
  meta.json        # 开始时间、源、编码参数、分片索引、暂停区间
```

- 崩溃恢复：启动时扫描 `.recording/` 下未正常关闭的会话，把 `init.mp4 + 全部分片` 顺序拼接并 remux 为标准 MP4（`-c copy -movflags +faststart`），进入"可恢复"列表供用户一键恢复。
- 正常停止：拼接 + remux + 生成缩略图 + 写入素材索引，最后删除分片。
- 磁盘保护：剩余空间 < 2 GB 或预计可录时长 < 5 分钟时提示并自动停止；写入失败立即停止并保住已有分片。

**为什么不用 MKV：** OBS 用 MKV 是因为"断电可恢复"，但 WebCodecs 侧没有成熟的 MKV muxer；fMP4 同样具备"分片即有效"的特性，且能被浏览器直接播放。

## 8. 导出与转码

| 导出场景 | 实现 | 说明 |
| --- | --- | --- |
| 原始导出（无编辑） | `ffmpeg -i in.mp4 -c copy -movflags +faststart out.mp4` | 秒级完成，无画质损失 |
| 裁剪/变速/音量 | ffmpeg 滤镜（`-ss/-to`、`setpts`、`atempo`、`volume`） | 视频重编码，优先硬件编码 |
| 背景/圆角/阴影/缩放 | WebCodecs 逐帧渲染（Canvas 合成）→ 新编码 → ffmpeg 封装 | 效果可预览、可复用；比 ffmpeg `zoompan` 的缓动更可控 |
| GIF | 先生成高质量 MP4，再 `palettegen/paletteuse` 两遍转 GIF | 限制 15s / 720p / 12fps，避免文件爆炸 |
| 仅音频 | `-vn -c:a aac` 或 mp3 | 播客/会议场景 |

硬件编码优先级：`h264_nvenc` → `h264_qsv` → `h264_amf` → `h264_videotoolbox` → `libx264`。启动时执行一次探测并缓存结果（`ffmpeg -encoders`）。

**ffmpeg 合规：** 只做封装/裁剪/转码时应使用 **LGPL 构建**（不启用 `--enable-gpl`、不含 libx264）；若为软件编码兜底而引入 libx264，构建变为 **GPL**，闭源分发需完成 GPL 合规（随包提供许可证并给出对应源码获取方式）；**带 `--enable-nonfree` 的构建不可再分发**，禁止直接随包发布。建议：默认只带 LGPL 构建 + 平台硬件编码，软编兜底用 WebCodecs 完成。当前内置二进制的实际情况：Windows 为 gyan.dev GPLv3 构建（无 nonfree，可分发但需 GPL 合规），macOS 两个为 evermeet 构建（含 `--enable-nonfree`，**发布前必须替换**）。替换方法与构建命令见 `resources/ffmpeg/README.md`。

## 9. 光标与键鼠可视化（最大的体验难点）

**硬约束：** Chromium 的屏幕采集会把光标合成进画面，Electron 未暴露"不采集光标"的开关。因此 **Screen Studio 那种"后期重绘光标、任意改变大小/平滑轨迹"的做法，在纯 Electron 采集链路里做不到**（否则会双光标）。

可行路径：

| 方案 | 能力 | 成本 | 结论 |
| --- | --- | --- | --- |
| A. 录制时叠加高亮（点击涟漪、光圈、按键浮层） | 教学场景足够，光标仍是原样 | 低 | ✅ P1 采用 |
| B. `screen.getCursorScreenPoint()` 20–60Hz 轮询记录轨迹 | 可做"放大跟随/自动缩放"的镜头调度；不能改光标外观 | 低 | ✅ P1 采用 |
| C. uiohook-napi 采集全局点击/按键 | 点击高亮、按键浮层、自动缩放触发点 | 中（原生模块 + macOS 辅助功能权限） | ✅ P1 评估 |
| D. 原生采集后端 + 自绘光标 | 完全后期可控 | 高（≥4 周 + 双平台） | ❌ V2 |

自动缩放算法（P1）：以点击点与光标停留点为兴趣点，做时间窗口聚类 → 生成 zoom 关键帧（进入 400ms、停留、退出 400ms，缓动 `easeInOutCubic`），限制最大放大 2.0×，并在镜头移动时给背景加轻微位移视差。

## 10. 编辑模型（非破坏式）

项目文件 `project.json` 只存"意图"，不存渲染结果：

```ts
type EditProject = {
  version: 1
  source: { file: string; durationMs: number; width: number; height: number; fps: number }
  canvas: { aspect: '16:9' | '1:1' | '9:16'; width: number; height: number; background: Background }
  clips: Array<{ startMs: number; endMs: number; speed: number }>  // 支持多段拼接
  audio: { systemGain: number; micGain: number; denoise: boolean }
  cursor: { scale: number; clickEffect: 'none' | 'ripple' | 'spotlight'; smooth: boolean }
  zooms: Array<{ startMs: number; endMs: number; x: number; y: number; scale: number; easing: string }>
  captions?: Array<{ startMs: number; endMs: number; text: string }>
  masks: Array<{ startMs: number; endMs: number; rect: Rect; style: 'blur' | 'pixelate' }>
  watermark?: { image: string; opacity: number; position: string }
}
```

- 预览：`<video>` 播放源文件 + Canvas 叠加层（缩放/背景/光标效果），保证 30fps 以上。
- 导出：按项目逐帧渲染（WebCodecs）或 ffmpeg 滤镜，两条路径共享同一套参数计算函数，避免"预览与导出不一致"。

## 11. IPC 契约

全部走 `contextBridge` 暴露的窄接口，禁止 renderer 直接访问 Node。

```ts
// src/shared/ipc.ts
export interface RecorderAPI {
  listSources(): Promise<SourceInfo[]>
  selectSource(id: string): Promise<void>
  start(config: RecordingConfig): Promise<{ id: string }>
  pause(): Promise<void>
  resume(): Promise<void>
  stop(): Promise<RecordingResult>
  onState(cb: (s: RecorderState) => void): () => void
  onLevel(cb: (l: { system: number; mic: number }) => void): () => void
}

export interface LibraryAPI {
  list(query?: LibraryQuery): Promise<Recording[]>
  rename(id: string, title: string): Promise<void>
  remove(id: string, toTrash: boolean): Promise<void>
  reveal(id: string): Promise<void>
  recover(id: string): Promise<Recording>
}

export interface ExportAPI {
  start(req: ExportRequest): Promise<{ jobId: string }>
  cancel(jobId: string): Promise<void>
  onProgress(cb: (p: ExportProgress) => void): () => void
}
```

| 通道 | 方向 | 载荷 | 备注 |
| --- | --- | --- | --- |
| `sources:list` | invoke | — | 含缩略图 dataURL、`display_id`、窗口图标 |
| `sources:select` | invoke | `{ id }` | 写入 handler 状态 |
| `recording:start` | invoke | `RecordingConfig` | Zod 校验 |
| `recording:chunk` | MessagePort | `ArrayBuffer` | 每 2s 一片，带序号 |
| `recording:state` | event | `RecorderState` | 主窗/控制条同时订阅 |
| `recording:level` | event | `{system,mic}` | 10Hz 节流 |
| `export:progress` | event | `{jobId,percent,etaMs}` | 1Hz 节流 |
| `permissions:status` | invoke | — | 返回各平台权限快照 |

安全基线：`contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`、严格 CSP、IPC 入参 Zod 校验、文件路径必须落在允许目录内（防目录穿越）。

## 14. 打包与发布

- electron-builder：Windows NSIS（x64）、macOS DMG（x64 / arm64 按 `arch` 分别打包，不要用 universal）、Linux AppImage。
- **ffmpeg 直接入库，不使用 `ffmpeg-static` 等 npm 包**：二进制按 `resources/ffmpeg/<platform>-<arch>/ffmpeg[.exe]` 提交（已内置 win32-x64、darwin-x64、darwin-arm64；Linux 暂缺，回退系统 ffmpeg）。
- 打包用 `extraResources` 而不是 `asarUnpack`：`win`/`mac` 各自 `from: resources/ffmpeg/<os>-${arch}` → `to: ffmpeg`，单平台安装包只带本平台的二进制，包内固定路径为 `<resources>/ffmpeg/ffmpeg[.exe]`。
- 运行时解析顺序（`src/main/ffmpeg.ts`）：打包态 `<resources>/ffmpeg/` → 开发态 `<项目根>/resources/ffmpeg/<platform>-<arch>/` → 系统 PATH；非 Windows 在 spawn 前 `chmod 755`，避免从 Windows 检出的仓库丢失可执行位。
- 发布门禁：`npm run dist` 先执行 `scripts/verify-ffmpeg.mjs`，校验二进制存在、体积合理、`-version` 可执行，防止缺失时静默降级为「仅原样导出」。
- macOS 需把 `Contents/Resources/ffmpeg/ffmpeg` 列入 `mac.binaries` 参与签名（hardened runtime 要求所有 Mach-O 都被签名）；二进制来源、版本、许可证与替换步骤见 `resources/ffmpeg/README.md`。
- Windows 签名推荐 Azure Trusted Signing（EV 证书成本高）；macOS 需 hardened runtime + notarization，entitlements：
  - `com.apple.security.device.audio-input`
  - `com.apple.security.device.camera`
  - Info.plist：`NSMicrophoneUsageDescription`、`NSCameraUsageDescription`、`NSAudioCaptureUsageDescription`（14.2+ 必需）
- 自动更新：`electron-updater` + 签名校验；灰度 10% → 50% → 100%；支持"跳过此版本"。
- 首启引导：权限检查 → 存储路径 → 快捷键确认 → 试录 5 秒。

## 15. 性能预算与优化点

| 项 | 预算 | 手段 |
| --- | --- | --- |
| 采集+编码 CPU（1080p30） | < 8% | 硬件编码、Worker 封装、无 Canvas 时直通编码 |
| 内存增量 | < 300 MB | 分片流式写盘、编码队列上限 8 帧、及时 `frame.close()` |
| 启动耗时 | < 2.5 s | 主窗懒加载编辑器、ffmpeg 探测异步化 |
| 停止到可预览 | < 2 s | 分片拼接 + `-c copy` remux，不转码 |
| 导出 1 分钟 1080p | 硬件 < 15 s / 软件 < 60 s | 编码器探测 + 多线程 |

其他：`powerSaveBlocker.start('prevent-display-sleep')` 防止录制中息屏；`win.setContentProtection(true)` 让控制条不被录进画面（Windows 10 2004+ / macOS）；录制器窗口 `backgroundThrottling: false`。

## 16. 测试策略

- 单元（Vitest）：时间轴换算、暂停区间、裁剪坐标与 DPI、码率计算、项目 schema 迁移。
- 集成（Playwright `_electron.launch`）：启动 → 选源 → 录 5 秒 → 停止 → 文件存在且可解析 → 导出成功。
- 媒体校验：`ffprobe` 断言时长、分辨率、帧率、音轨存在、首帧可解码。
- 手工矩阵：Win10/Win11 × 单屏/双屏/不同缩放（100/125/150/200%）× 集显/独显；macOS 13/14/15。
- 异常注入：拔掉麦克风、拒绝权限、磁盘写满、录制中 kill -9、休眠唤醒、切换显示器。
- 性能基线：固定 10 分钟 1080p30 录制，记录 CPU/内存/丢帧，纳入 CI 夜间任务。

## 17. 风险与 POC 清单（第 1 周必须全部有结论）

| ID | 验证项 | 判定标准 | 失败预案 |
| --- | --- | --- | --- |
| POC-1 | `setDisplayMediaRequestHandler` + `audio:'loopback'` | Win11 录 10s，回放有系统声且电平正常 | 改用 ffmpeg WASAPI loopback 采集音频 |
| POC-2 | `VideoEncoder` H.264 硬编 + mp4-muxer 实时落盘 | 4K30 录 10min，无丢帧，文件可播放/可 seek | 降级 1080p 或 MediaRecorder(WebM) + ffmpeg 转封装 |
| POC-3 | 暂停/续录时间戳 | 暂停 30s 后总时长正确，无跳帧/音画不同步 | 分片独立成段，停止时拼接 |
| POC-4 | macOS 14.2+ 系统音频权限 | 授权/拒绝两条路径 UI 都正确，拒绝时明确报错 | 降级"仅麦克风"并常驻提示 |
| POC-5 | 区域裁剪画质与开销 | 4K 屏裁 1080p 区域，文字清晰，CPU < 12% | 改为录制后裁剪（画质不变，码率浪费） |
| POC-6 | 崩溃恢复 | `taskkill /f` 后重启，恢复到最后 2s 内 | 缩短分片到 1s |
| POC-7 | `AudioEncoder` AAC 可用性 | 能直接产出 AAC 轨道 | PCM/Opus 旁路 + 停止时 ffmpeg 编码 |
| POC-8 | uiohook-napi（Electron 45 / Win11 / macOS） | 能拿到全局点击与按键，权限流程可控 | 仅用光标轮询做自动缩放，不做按键浮层 |
| POC-9 | ffmpeg 硬件编码探测 | 三家 GPU 至少各一台机器验证通过 | 统一软编 + 提示"导出较慢" |
| POC-10 | 打包体积与内置 ffmpeg | 单平台安装包 < 120 MB，`<resources>/ffmpeg` 中的二进制可执行 | 裁剪 ffmpeg（`--disable-everything` 只保留所需 muxer/encoder）或首次启动按需下载（需签名校验）；当前实测 Win x64 NSIS 140 MB，超预算 |
